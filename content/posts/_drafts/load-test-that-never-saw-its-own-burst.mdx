**Short answer:** if a test asserts a ceiling on something it counts under load, check what it counts and when it counts it. Ours counted every connection on a shared test database, so a neighbour's lingering sockets looked like our burst. And its own samples were taken before any of its connections had finished starting, so when it ran alone it read almost nothing and passed. Tag your own connections and count only the tag, sample from a connection that exists before the work starts, prove that the tag is visible, and hold the burst still with a barrier if you need an exact number.

**Status of what this describes:** a test-only change in Northsun's private repository, merged on 6 October 2026. It changes no served code, and nothing here is a claim about how any service behaves. The toy in this post is a stand-in written to show the shape of the measurement problem. It is not a database and not Northsun's test, and its numbers are its own.

**Who did the work:** Northsun's delivery agents found the failure, rewrote the test and ran the review rounds described here, not me. They are AI sessions working under written rules, and automated reviewers checked the change. The toy and the runs of it in this post were done on 7 October 2026 by the AI session that drafts these write-ups, not by me and not by the agents who wrote the test. Where this post says "we", it means the agents and the Northsun project.

## What happened

Northsun is the memory and enrichment layer for AI agents.

One of our tests drives a burst of concurrent requests of three kinds through the code and asserts that the number of open database connections stays under a ceiling with room to spare. The code under test opens one database client per request, so the test is there to catch a request that forgets to close its own. It sits in a shared test database that every test file in the suite uses.

In one night it failed on two unrelated pull requests, with a count above its budget, under the load of the full suite. Run alone, it passed. Nothing in either pull request touched the code it covers.

## What it was actually counting

The record of the investigation found two separate problems, and either one alone would have made the test untrustworthy.

**It counted the whole container.** The test counted every connection that the application's database role held on the shared database server. Under a full-suite run, earlier test files had left sockets lingering until their idle timeout, which is longer when the machine is starved of CPU, and background writes were still in flight. Those neighbours were in the count. The failure was them, not the scenario.

**It never saw its own burst.** The old samples were requests queued on one shared administrative connection, and they were queued in the same synchronous loop that started the burst. They ran before any of the burst's connections had finished starting up, so the server did not yet report them. Instrumented with a tag, the old shape read about zero of the scenario's own connections at every sample when the test ran alone. The solo green was not evidence of headroom. It was a test that had measured nothing and been happy about it. The check that the count was above zero only held because the administrative connection itself was in the total.

There was a third problem under both. The budget was never true. The scenario opens one connection per unit of work, by construction. Half-headroom for that many simultaneous requests would mean bounding concurrency in production, which is a product decision and not a test tolerance. Sampled peaks of the unconstrained burst read lower than the number of units only because of when the samples happened to land.

## A toy that shows the shape of it

A real multi-connection database was not available for this write-up, so here is a TCP stand-in. A small server counts connections per tag. Like a database's activity view, it learns a connection's tag only once the startup message ("HELLO tag") has been handled, which takes a moment. A unit of work opens a connection, says hello with a tag, makes one request and closes. A neighbour holds a connection under its own tag and does nothing.

```js
// toy.mjs: a TCP "database" that counts connections per tag. Like pg_stat_activity, it knows a
// connection's tag only once the startup message ("HELLO <tag>") has been handled, which takes a moment.
import net from "node:net";
const WORK_MS = Number(process.env.WORK_MS ?? 15); // how long the server takes over one request

export function startServer() {
  const conns = new Set(); // { tag, blocked }
  let barrier = null; // while set, a request waits for it
  const server = net.createServer((sock) => {
    const c = { tag: null, blocked: false };
    conns.add(c);
    let buf = "";
    sock.on("data", (d) => {
      buf += d;
      for (let i; (i = buf.indexOf("\n")) >= 0; ) {
        const line = buf.slice(0, i); buf = buf.slice(i + 1);
        if (line.startsWith("HELLO ")) setTimeout(() => (c.tag = line.slice(6)), 3);
        else if (line === "COUNT") sock.write(JSON.stringify(stats()) + "\n");
        else if (line === "WORK") {
          const done = () => { c.blocked = false; sock.write("OK\n"); };
          if (barrier) { c.blocked = true; barrier.then(done); } else setTimeout(done, WORK_MS);
        }
      }
    });
    sock.on("close", () => conns.delete(c));
    sock.on("error", () => conns.delete(c));
  });
  const stats = () => ({
    all: [...conns].filter((c) => c.tag !== null).length, // every connection that has finished starting up
    byTag: [...conns].reduce((m, c) => (c.tag && (m[c.tag] = (m[c.tag] || 0) + 1), m), {}),
    blocked: [...conns].filter((c) => c.blocked).length,
  });
  return {
    listen: () => new Promise((r) => server.listen(0, "127.0.0.1", () => r(server.address().port))),
    close: () => server.close(),
    stats,
    hold: () => { let go; barrier = new Promise((r) => (go = r)); return () => { barrier = null; go(); }; },
  };
}

// One unit of work: open a connection, introduce yourself with a tag, make one request, close.
export function unit(port, tag, { leak = false } = {}) {
  return new Promise((resolve) => {
    const s = net.connect(port, "127.0.0.1", () => s.write(`HELLO ${tag}\nWORK\n`));
    s.on("data", () => { if (leak) resolve(); else s.end(); }); // a leaking unit forgets to close
    s.on("close", resolve);
    s.on("error", resolve);
  });
}

// A neighbour: holds a connection open under its own tag and does nothing.
export function neighbour(port) {
  const s = net.connect(port, "127.0.0.1", () => s.write("HELLO neighbour\n"));
  return s;
}
```

The demo reads "how many connections did my burst open?" five ways:

```js
// demo.mjs: five ways to read "how many connections did MY burst open?"
import net from "node:net";
import { startServer, unit, neighbour } from "./toy.mjs";
const UNITS = 80, NEIGHBOURS = 50, TAG = "own-" + Math.random().toString(16).slice(2, 8);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const server = startServer();
const port = await server.listen();
const burst = (opts) => Array.from({ length: UNITS }, (_, i) => unit(port, TAG, opts?.(i)));

// 1. Count every connection on the shared server, with a neighbour holding some of them.
const held = Array.from({ length: NEIGHBOURS }, () => neighbour(port));
await sleep(50);
let allPeak = 0, ownPeak = 0;
const poll = setInterval(() => { const s = server.stats(); allPeak = Math.max(allPeak, s.all); ownPeak = Math.max(ownPeak, s.byTag[TAG] || 0); }, 2);
await Promise.all(burst());
clearInterval(poll);
console.log(`1. neighbour holds ${NEIGHBOURS}, ${UNITS} units run. Peak counting every connection: ${allPeak}. Counting only our tag: ${ownPeak}.`);

// 2. Samples queued with the work: asked over an already-open control socket in the same loop that starts the burst.
held.forEach((s) => s.destroy());
await sleep(50);
const control = net.connect(port, "127.0.0.1");
await sleep(20);
const queued = [];
control.on("data", (d) => d.toString().trim().split("\n").forEach((l) => queued.push(JSON.parse(l))));
const work2 = [];
for (let i = 0; i < UNITS; i++) { work2.push(unit(port, TAG)); control.write("COUNT\n"); }
await Promise.all(work2);
await sleep(30);
console.log(`2. ${queued.length} samples queued with the burst read our connections: at most ${Math.max(...queued.map((s) => s.byTag[TAG] || 0))}.`);

// 3. A dedicated sampler on a timer, started before the workload, over five identical runs.
const peaks = [];
for (let r = 0; r < 5; r++) {
  let peak = 0;
  const t = setInterval(() => { peak = Math.max(peak, server.stats().byTag[TAG] || 0); }, 2);
  await Promise.all(burst());
  clearInterval(t);
  peaks.push(peak);
}
console.log(`3. a timer sampler saw peaks of ${peaks.join(", ")} of ${UNITS} across five identical runs.`);

// 4. A barrier: the server holds every request until released, so every unit is provably open and blocked.
const release = server.hold();
const work4 = burst();
let seen;
for (let i = 0; i < 2000 && !seen; i++) {
  const s = server.stats();
  if ((s.byTag[TAG] || 0) >= UNITS && s.blocked >= UNITS) seen = s;
  else await sleep(2);
}
release();
await Promise.all(work4);
await sleep(30);
console.log(`4. barrier: ${seen?.byTag[TAG]} of our connections open, ${seen?.blocked} blocked (exact); after release ${server.stats().byTag[TAG] || 0} left.`);

// 5. A leak: one unit in ten forgets to close. The ownership check after the work settles catches it.
await Promise.all(burst((i) => ({ leak: i % 10 === 0 })));
await sleep(30);
console.log(`5. one unit in ten leaks: ${server.stats().byTag[TAG] || 0} of our connections left open after the work settled (expected 0).`);
server.close(); control.destroy(); process.exit(0);
```

Run with `WORK_MS=3 node demo.mjs` (the server takes only a few milliseconds per request, so the burst is short). One run on Node 22.22.0:

```text
1. neighbour holds 50, 80 units run. Peak counting every connection: 91. Counting only our tag: 41.
2. 80 samples queued with the burst read our connections: at most 0.
3. a timer sampler saw peaks of 28, 26, 28, 47, 38 of 80 across five identical runs.
4. barrier: 80 of our connections open, 80 blocked (exact); after release 0 left.
5. one unit in ten leaks: 8 of our connections left open after the work settled (expected 0).
```

Lines 1 and 3 change from run to run, and that is part of the point. Lines 2, 4 and 5 did not change in any run: 80 samples queued with the burst read zero every time, the barrier read exactly 80, and the leak left exactly 8 connections open. On Node 22.22.2 the same script gave the same pattern, with peaks of 58, 45, 29, 44 and 1 on line 3. Without `WORK_MS` the server takes longer per request, which makes the toy's burst long enough for a timer sampler to see all of it every time (peaks of 80 in all five runs). That is why the toy takes `WORK_MS` as a setting: how well a sampler sees a burst depends on how long each connection lives.

What the toy shows: counting every connection on a shared server includes the neighbours (line 1); samples queued with the work, over a connection that already exists, run before the work's connections are visible (line 2); a sampled peak is a measurement of the sampler as much as of the burst (line 3); a barrier gives an exact count (line 4); and the property that matters for a leak is "zero left once the work settles" (line 5). What it does not show: how a real database or a real client library behaves, or anything about Northsun's numbers.

## What fixed the measurement

The change made the test measure only what its own scenario does, in five moves.

1. **Tag your own connections.** Every connection URL the test hands to the code under test now carries a per-run application name. The server reports that name per connection, so the test counts the tag and nothing else. A neighbour can neither inflate the count nor hide a leak.
2. **Sample from a connection that exists before the work.** A dedicated sampler connection is opened and warmed first, takes one sample before the burst and asserts that it reads exactly zero tagged connections, and only then starts the workload. The client library connects lazily, so a sampler created after the burst started could finish after it and record a low partial peak or a post-burst zero.
3. **Prove the tag is visible.** A separate arm opens a connection from the same helper and asserts that it shows under the tag while live and is gone once ended. If the tag were ever dropped, say by a driver upgrade that rebuilds the URL without its query string, every other assertion would pass while measuring nothing.
4. **Assert ownership, not just a peak.** The exact claim is that zero tagged connections remain the instant the work settles. A sampled peak is a tripwire for gross over-opening and not a meter: a version that opens one extra short-lived connection per unit stays under the ceiling and is caught only by the ownership assertion.
5. **Replace the timing-dependent floor with a barrier.** A first version required the peak to reach half the units, but a correct run on a fast database can read under that, so the floor was itself flaky. The final version takes locks on the three tables that the units write, from a second connection, before the burst. Every unit's first statement then waits on a lock, and a unit can only wait while holding an open connection, so while the locks are held every unit is provably open and none can finish. The sampler polls until it sees every unit's connection open and blocked on a lock, then the test asserts the exact count.

## What the review rounds found

The record shows automated reviewers finding a different way the test could pass or fail without measuring, in each round. The first fix of the sampler had it connect lazily, after the work had started, which could finish after the burst. A failure in the middle of the test left a privileged client open on the shared server, until the sampler's close moved into an outer `finally`. The timing-dependent floor became the barrier. And a rejected unit made `Promise.all` return on the first failure while the others kept running, against a database the next test file was about to use. The cleanup now releases the barrier, waits for every unit with `allSettled`, closes, and only then rethrows the original error. Each of those has a planted-failure arm, and the record says each deliberate breakage of the test (a connection that is never closed, extra connections held per unit, the tag dropped, the barrier removed, `allSettled` removed) makes it fail.

## What this still does not prove

- A sampled peak is a tripwire for gross over-opening, not a per-unit meter. The record plants one extra short-lived connection per unit and shows it is not caught by the peak, only by the ownership assertion.
- The ceiling's headroom for this workload is small. A bigger burst or another kind of unit breaches it, and that is the signal.
- The tag makes the test independent of what ran before it. It does not make it independent of a neighbour that opens more than the container allows.
- The toy is a toy. It shows the shape of the measurement problem on a TCP server, not the behaviour of any database, and no number from it says anything about Northsun.
- The review rounds are as the record reports them. They were not re-run for this post.

## How to check your own test

Four questions, in order. What exactly does the count include: can a neighbour appear in it? When does the first sample run: before or after the thing it counts is visible? What happens if the thing you tagged is no longer tagged: does anything fail? And does the test hold the burst still, or does it hope the sampler lands on the peak? If a test passes when run alone, make it fail on purpose first: hold sixty connections from another process and see what it says.

## FAQ

### Why did the test pass alone and fail in the full suite?

It counted every connection on a shared database, so it passed when nobody else had any open and failed when earlier test files had left sockets lingering. Run alone, it also read almost none of its own connections, so even a leak would have passed.

### Can't I just raise the budget?

Not honestly. The budget was already above what the scenario opens, so raising it would only hide the neighbours. The question to ask first is whether the test counts what it claims to count.

### Should a load test assert on a sampled peak at all?

As a tripwire for gross over-opening, yes. As the exact claim, no: a sampled peak depends on when the samples land. Assert on something exact, such as zero of your own connections left after the work settles, and use a barrier when you need an exact peak.
