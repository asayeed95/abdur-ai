**Short answer:** if a test asserts a ceiling on something it counts under load, check what it counts and when it counts it. Northsun's test counted every connection its database role held on a shared test database, so earlier files' leftovers looked like its own burst. And it took its samples before its own connections existed, so when it ran alone it read none of them and passed. Tag your own connections and count only the tag, sample from a connection that already exists, prove that the tag reaches the server, and hold the burst still with a barrier if you need an exact number.

**Status of what this describes:** a test-only change in Northsun's private repository, merged on 6 October 2026 as pull request 1612. Merged is not deployed, and this change deploys nothing: it changes no served code, and nothing here is a claim about how any service behaves. The script in this post is a stand-in I describe below. It runs against a scratch Postgres, it is not Northsun's test, and its numbers are its own.

**Who did the work:** not me. The failure was reported and filed as a task inside Northsun's agent workflow, a build agent (an AI session working under written rules) rewrote the test, and an automated reviewer raised the findings described below. The script and the runs of it in this post were done on 7 October 2026 by the AI session that drafts these write-ups, not by me and not by the agent who wrote the test. Where this post says "Northsun", it means that project and its agents.

**Terms, as this post uses them.** A *connection* is one open session between a client and the database server, and it occupies one of a fixed number of slots on the server. The *activity view* is Postgres's `pg_stat_activity`, which lists every open connection with, among other fields, its `application_name` (a label the client chooses and sends when it connects) and what the connection is waiting on. A *unit of work* is one request through the code, which here opens one connection. A *sampler* polls the activity view to count connections while work runs. A *barrier* stops every unit from finishing until the test says go.

## What happened

Northsun is the memory and enrichment layer for AI agents.

One of Northsun's tests drives a burst of concurrent requests of three kinds through the application code and asserts on how many database connections the burst opens. The code opens one database client per request, so the test is there to catch a request that forgets to close its own. It runs against a database container that the suite's real-database test files share, connecting as one database role. Its ceiling was set at half of the database's usable connection slots.

In one night it went red on two pull requests, under the load of the full suite, with a count above that ceiling. Run alone, it passed. The merged test's own header calls the two pull requests unrelated to it.

## What it was actually counting

The decision record names three things wrong. The first two made the test unreliable. The third made its ceiling untrue.

**It counted the whole container.** The test counted every connection the application's database role held on the shared server. The record attributes the extra connections in the failing runs to earlier test files' sockets, which linger until an idle timeout (longer, the record notes, when the machine is starved of CPU), and to background writes still in flight. Those were in the count, so the red was the neighbours and not the scenario. The record reproduced it on demand: a scratch file held a pile of untagged connections while the test ran, and the old test went red three times out of three while the new one went green three times out of three.

**It never saw its own burst.** The old samples were queued on one shared administrative connection, in the same synchronous loop that started the burst. They ran before any of the burst's connections had finished their handshake with the server. Instrumented with a tag, the old shape read none of the scenario's own connections at any sample when the test ran alone. The solo green was not evidence of headroom. It was a test that had measured nothing and been happy about it. Its check that the count was above zero held only because the administrative connection was itself in the total.

**The ceiling was never true.** The code opens one connection per unit of work, by construction, and the scenario has more units than half the usable slots. A ceiling at half the slots could only pass if the samples missed the burst, and sampled peaks of the unconstrained burst read lower than the unit count only because of when the samples happened to land. Holding the burst under that ceiling would mean bounding concurrency in production, which is a product decision and not a test tolerance, so the record rejected widening the number as well.

## The same readings on a real Postgres

To see the shapes without Northsun's private test, here is a script that reads "how many connections did my burst open?" five ways on a scratch database. It uses the same client library as the Northsun test, postgres.js, which connects lazily: a client opens its connection when it first needs one. It needs a local Postgres and the `postgres` npm package, for example `createdb burstdemo`, then `npm i postgres`, then `PGURL=postgres://postgres@127.0.0.1:5432/burstdemo node demo.mjs`, with the URL adjusted to your server. Each unit of work is one client, one insert, then close. A neighbour is a client that holds a connection open under its own label and does nothing.

```js
// demo.mjs: five ways to read "how many connections did MY burst open?" on a real Postgres.
// Run: PGURL=postgres://postgres@127.0.0.1:5432/burstdemo node demo.mjs   (npm i postgres first)
import postgres from "postgres";
const URL = process.env.PGURL, UNITS = 40, NEIGHBOURS = 25;
const TAG = "own-" + Math.random().toString(16).slice(2, 8);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const client = (name) => postgres(URL, { max: 1, onnotice: () => {}, connection: { application_name: name } });

const admin = client("admin"); // the shared administrative connection every sample goes through
await admin`create table if not exists burst_demo (n int)`;
const count = () => admin`
  select count(*) filter (where pid <> pg_backend_pid())::int                          as every,
         count(*) filter (where application_name = ${TAG})::int                        as own,
         count(*) filter (where application_name = ${TAG} and wait_event_type = 'Lock')::int as waiting
  from pg_stat_activity where backend_type = 'client backend' and datname = current_database()`.then((r) => r[0]);

const leaked = [];
// One unit of work: its own client, one statement, then close (unless it leaks).
const unit = async ({ leak = false } = {}) => {
  const sql = client(TAG);
  await sql`insert into burst_demo values (1)`;
  if (leak) leaked.push(sql); else await sql.end();
};
const burst = (opts) => Array.from({ length: UNITS }, (_, i) => unit(opts?.(i)));
// A sampler that polls as fast as the administrative connection answers, until told to stop.
const sampleWhile = (work) => { const peak = { every: 0, own: 0 }; let on = true;
  const loop = (async () => { while (on) { const s = await count(); peak.every = Math.max(peak.every, s.every); peak.own = Math.max(peak.own, s.own); } })();
  return Promise.all(work).then(async () => { on = false; await loop; return peak; }); };

// 1. Count every connection in the shared database, with a neighbour holding some of them.
const held = Array.from({ length: NEIGHBOURS }, () => client("neighbour"));
await Promise.all(held.map((s) => s`select 1`));
const p1 = await sampleWhile(burst());
console.log(`1. neighbour holds ${NEIGHBOURS}, ${UNITS} units run. Peak counting every connection: ${p1.every}. Counting only our tag: ${p1.own}.`);

// 2. Samples queued with the work: asked on the already-open administrative connection in the same loop that starts the burst.
await Promise.all(held.map((s) => s.end())); await sleep(100);
const work2 = [], queued = [];
for (let i = 0; i < UNITS; i++) { work2.push(unit()); queued.push(count()); }
const reads = await Promise.all(queued); await Promise.all(work2);
console.log(`2. ${reads.length} samples queued with the burst read our connections: at most ${Math.max(...reads.map((s) => s.own))}.`);

// 3. A dedicated sampler started before the workload, over five identical runs.
const peaks = [];
for (let r = 0; r < 5; r++) peaks.push((await sampleWhile(burst())).own);
console.log(`3. a sampler started first saw peaks of ${peaks.join(", ")} of ${UNITS} across five identical runs.`);

// 4. A barrier: a second connection locks the table the units write, so every unit blocks on a lock from an open connection.
let release; const gate = new Promise((r) => (release = r)); let locked; const lockedP = new Promise((r) => (locked = r));
const locker = client("locker");
const lockerDone = locker.begin(async (tx) => { await tx`lock table burst_demo in access exclusive mode`; locked(); await gate; });
await lockedP;
const work4 = burst();
let seen; for (let i = 0; i < 2000 && !seen; i++) { const s = await count(); if (s.own >= UNITS && s.waiting >= UNITS) seen = s; else await sleep(5); }
release(); await lockerDone; await locker.end(); await Promise.all(work4);
console.log(`4. barrier: ${seen?.own} of our connections open, ${seen?.waiting} waiting on a lock; after release ${(await count()).own} left.`);

// 5. A leak: one unit in ten forgets to close. The ownership check after the work settles catches it.
await Promise.all(burst((i) => ({ leak: i % 10 === 0 })));
console.log(`5. one unit in ten leaks: ${(await count()).own} of our connections left open after the work settled (expected 0).`);
await Promise.all(leaked.map((s) => s.end())); await admin.end();
```

One run on Node 22.22.0, postgres.js 3.4.9 and PostgreSQL 16.14:

```text
1. neighbour holds 25, 40 units run. Peak counting every connection: 64. Counting only our tag: 39.
2. 40 samples queued with the burst read our connections: at most 0.
3. a sampler started first saw peaks of 26, 31, 36, 39, 40 of 40 across five identical runs.
4. barrier: 40 of our connections open, 40 waiting on a lock; after release 0 left.
5. one unit in ten leaks: 4 of our connections left open after the work settled (expected 0).
```

Across ten runs of this listing, five on Node 22.22.0 and five on Node 22.22.2, lines 2, 4 and 5 read the same every time: the samples queued with the burst read at most 0, the barrier saw exactly 40 connections open and 40 waiting on a lock with 0 left after release, and the leak left exactly 4 open. Lines 1 and 3 changed from run to run. On line 1 the peak counting every connection read 63 to 65 and the tagged peak read 38 to 40, and on line 3 the five peaks in a run ran from 23 to 40 of 40.

What the script shows, with its limits. Line 1: counting every connection in a shared database includes the neighbours, and even the tagged count is itself a sampled peak, so it can read below the true number. The Northsun test counted by database role where this script counts by database, which has the same flaw. Line 2: samples queued over an already-open connection in the same loop that starts the burst run before the burst's connections exist, so they read zero. That is consistent with the record's account of the old test, and it is a reading of this script and not a replay of that test. Line 3: even a sampler started first reports a peak that changes from run to run, because each unit's connection lives only briefly. Line 4: a barrier makes the count exact, and the sampler waits on the lock wait event, not just on a count. Line 5: the property that catches a leak is "zero of my connections left once the work settles". What it does not show: how Northsun's database, role or code behave, or anything about Northsun's numbers.

## What fixed the measurement

The change made the test measure only what its own scenario does, in five moves.

1. **Tag your own connections.** Every connection URL the test hands to the code under test carries a per-run application name. The server reports that name per connection, so the test counts the tag and nothing else. The tag is unique per run, so a neighbour can neither inflate the count nor hide a leak.
2. **Sample from a connection that exists before the work.** A dedicated sampler connection is opened and warmed with one query first, takes one sample before the burst and asserts that it reads exactly zero tagged connections, and only then starts the workload. This came out of a review finding: the client library connects lazily, so a sampler whose first query was issued after the work had started could finish after it and record a low partial peak or a post-burst zero.
3. **Prove the tag reaches the server.** A separate arm opens one connection through the same helper and the same client library, and asserts that it shows under the tag while live and is gone once ended. The test's own comment names the case it guards: if the tag were ever dropped, say by a driver upgrade or a URL rebuilt without its query string, the tagged count would read zero and the ceiling and ownership assertions, which expect small numbers, would pass without measuring anything. In the record's breakage run, dropping the tag turned both this arm and the burst arm red.
4. **Assert ownership, not just a peak.** The exact claim is that zero tagged connections remain the instant the work settles. The old check compared all connections after the work with a baseline taken before it, which a neighbour's connection opening between the two reads could turn red. A sampled peak stays as a tripwire for gross over-opening and not as a meter: the record plants one extra short-lived connection per unit of one kind, measures a peak that plateaus below the ceiling, and says the peak does not catch it. A version that leaks its connections is caught by the ownership assertion.
5. **Replace the timing-dependent floor with a barrier.** A floor added in the first review round required the peak to reach half the units, but a correct run on a fast database or a contended runner can read under that, and a valid reduction in concurrency would fail it too. The final version holds the burst still. A second connection takes `ACCESS EXCLUSIVE` locks on the three tables the units write, before the burst starts. Every unit's first statement then waits on a lock, and a unit can only wait from an open connection, so while the locks are held every unit's connection is provably open and none can finish. The sampler polls until it sees every unit's connection open and waiting on a lock, then the test asserts the exact count. The barrier is Postgres's own, so the code under test is unchanged. If the code ever opens fewer connections than there are units, the barrier is never reached and the test fails by name after a deadline, on purpose: a change in connections per unit should change that number knowingly.

## What the review rounds found

The record shows an automated reviewer raising four findings on the pull request across three rounds. Each was a different way the test could pass or fail without measuring.

- **Round two, first finding:** the sampler connected lazily, after the work had started, which could finish after the burst. It now exists before the work (move 2).
- **Round two, second finding:** a failure in the middle of the test left a privileged client open on the shared server, until the sampler's close moved into an outer `finally` that always runs.
- **Round three:** the half-the-units floor was timing-dependent. It became the barrier (move 5).
- **A later finding:** a rejected unit made `Promise.all` return on the first failure while the other units kept running against a shared database, where late writes could contaminate the next test file. The cleanup now releases the barrier first, waits for every unit with `allSettled`, closes the connections, and only then rethrows the original error.

Two kinds of check back the changes, both as the record reports them and not re-run for this post. First, the author ran the test against deliberately broken copies and reports red for each: a connection that is never closed, extra connections held per unit, the tag dropped from the URL, the barrier removed, the sampler readied after the work starts, and `allSettled` removed. The last one was caught on every run, but only one arm caught it every time: the arm where a unit rejects catches it on three runs of five, because the other units may finish before the cleanup looks, so a second arm that fails while every unit is still blocked at the barrier does the deterministic work. Second, three planted-failure arms in the test itself make the burst fail on purpose and assert that the planted error is the one reported, that every unit had settled when the function returned, and that no lock or tagged connection remains.

## What this still does not prove

- A sampled peak is a tripwire for gross over-opening, not a per-unit meter. The extra short-lived connection the record plants is not caught by the peak, only a leak is caught by the ownership assertion.
- The ceiling's headroom for this workload is small. A bigger burst or another kind of unit breaches it, and that is the signal.
- The tag makes the test independent of what ran before it. It does not make it independent of a neighbour that opens more than the container allows.
- The change is test-only and merged. It says nothing about how Northsun's service performs or behaves in production.
- The script is not Northsun's test. It counts by database where the real test counted by role, and no number from it says anything about Northsun.
- The review rounds, the breakage runs and the green runs are as the decision record reports them. They were not re-run for this post, and the Northsun repository is private.

## How to check your own test

Four questions, in order. What exactly does the count include: can a neighbour appear in it? When does the first sample run: before or after the thing it counts exists? What happens if the thing you tagged is no longer tagged: does anything fail? And does the test hold the burst still, or does it hope the sampler lands on the peak? If a test passes when run alone, make it fail on purpose first: hold a pile of connections open from another process and see what it says.

## FAQ

### Why did the test pass alone and fail in the full suite?

Two reasons, from the record. It counted every connection its role held on a shared database, so it passed when nothing else was open and went red when earlier test files had left connections behind. And its samples ran before its own connections existed, so alone it read none of them, which means a pass alone said nothing about headroom.

### Can't I just raise the ceiling?

The record rejected it. The old ceiling was below the number of connections the scenario opens by construction, so it only passed when the samples missed the burst, and a higher number would still have been counting neighbours. Once the test counts only its own connections, the ceiling can be structural: at most one connection per unit of work, and below the usable slots.

### Should a load test assert on a sampled peak at all?

As a tripwire for gross over-opening, yes. As the exact claim, no, because a sampled peak depends on when the samples land. Assert on something exact, such as zero of your own connections left once the work settles, and use a barrier when you need an exact peak.
